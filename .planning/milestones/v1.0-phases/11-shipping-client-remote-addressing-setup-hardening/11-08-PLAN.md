<objective>
Close the four source-verified trust-boundary findings from the third external design review ("FAMP v1.0 Remote Addressing: Final Design Review", archived at `DESIGN-REVIEW-C-final.pdf`; verification in `11-REVIEW-C-FINDINGS.md`). All four sit on the review's own required-before-v1.0.0 list.

The shape of the problem: plan 11-07 bound the SENDER identity at both local boundaries (broker `from.name()`, egress `from.authority()`). This plan binds the DESTINATION and the FIELD OWNERSHIP — the two remaining places where a signed envelope's meaning is decided by something other than what the sender actually signed.

- **F-1 (worst)** — `inbox_handler` (ingress.rs:162) reads the recipient from the URL path (:167) and delivers to `recipient.name()` (:225). It never reads `envelope.to`. The gateway also has no check that it owns the destination domain. Any pinned peer can place a signed envelope in any local mailbox, or use the gateway as an open relay. `SignedEnvelope::federation_format_ok` (famp-envelope/src/envelope.rs:531) has ZERO callers, so inbound `nonce`/`expiry` are never even format-checked.
- **F-2** — `sign_federation_fields` (egress.rs:89) inserts all five federation fields with `entry().or_insert_with()` (:108-116) — preserve-if-present — then signs at :124. `capability` and `approval` are never touched at all. A local agent that speaks the UDS protocol gets the gateway to sign attacker-chosen federation metadata under its federation identity.
- **F-3** — the route map is a peer-domain x backed-name cross-product (main.rs:283-289), manufacturing principal->route bindings the operator never configured. Since `to` is client-controlled, those fabricated bindings are reachable by a local agent.
- **F-4** — duplicate `--peer` domains are accepted (main.rs:148 pushes into a Vec with no dedup) and resolve last-write-wins via `HashMap::insert` (famp-transport-http/src/transport.rs:80-82). Flag order silently changes every destination for a domain.

Purpose: make the receiving side authoritative only for what it owns, and make federation metadata mean what the gateway asserts rather than what a local client suggested.
Output: three boundary fixes with adversarial tests, existing gates green as the controls.

Sequencing: wave 3, and it MUST land BEFORE 11-04 and 11-05. Both of those are written against the gateway config surface this plan changes — 11-04 builds the shipping-surface E2E harness that drives gateway flags, and 11-05 rewrites `docs/GATEWAY-SETUP.md`'s flag table. Running them first means writing tests and docs twice.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| remote peer -> local mailbox (ingress) | a verified signature proves authorship, NOT that this gateway should accept or where it should deliver |
| local agent -> gateway federation metadata (egress) | the gateway signs a field block a local client can pre-populate |
| operator config -> route map | flag parsing decides which remote principals this gateway will sign for and where it sends them |
