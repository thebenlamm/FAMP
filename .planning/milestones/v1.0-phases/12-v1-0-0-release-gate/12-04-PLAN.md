<objective>
REL-05 (version bump) + REL-03 (green-gate attestation at the exact tag commit) — bump the workspace from the release candidate to `1.0.0` in one atomic commit, push it, and then prove with a live GitHub query that THAT SHA has a fully green CI run, recording the run ids in the phase record.

Purpose: this is the commit the `v1.0.0` tag will point at, and it is the only commit in Phase 12 guaranteed to touch paths `ci.yml` does not ignore. Everything about its shape is load-bearing.

Output: one bump commit, one attestation record naming the tag-candidate SHA and its run ids.

**Two failure modes this plan exists to prevent.**

1. **A partial bump self-inflicts a red CI run.** The version string is deliberately duplicated across `Cargo.toml`, the `BANNER_ABOUT` const, and the test that pins both — that duplication IS the drift gate (VER-02). Bumping the manifests without the const and the test literals makes `version_strings_unified` fail, and that failure looks exactly like a real regression. Member crates use `version.workspace = true` so their own `[package]` version follows the root automatically, but every internal path-dependency declaration carries its own explicit pin that does NOT follow — 51 of them across 13 manifests.

2. **Attesting CI green against the wrong evidence.** `.github/workflows/ci.yml` sets `paths-ignore: ["docs/**", ".planning/**", "**/*.md"]`. A commit touching only those paths triggers **zero check-runs — not a skip, not a pass, no check-run object at all.** `.planning/REQUIREMENTS.md` line 89 already contains a false claim built on this trap (it names a docs-only commit as CI's green run; that commit was never run through CI). Never trust a written "CI is green on X" claim — including that one. Re-query the exact SHA at the moment of attestation.
</objective>
