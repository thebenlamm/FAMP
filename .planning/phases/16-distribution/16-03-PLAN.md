<objective>
Prove DIST-03 mechanically with a falsification pair: one test that MUST FAIL if checksum verification is
removed from the installer, and one that MUST STILL PASS under the same removal.

Purpose: this project's standing rule is that a falsification run needs a control — a check that is green
under both the working and the broken state carries zero information. A single "installer rejects a bad
checksum" test can pass for the wrong reason (a 404, a missing archive, a tar failure) and would still be
green if verification were deleted. The pair discriminates.

Output: `crates/famp/tests/installer_checksum_gate.rs` with two named tests, running under CI's existing
workspace test job with no new dependency.
</objective>

  <action>
    Write the two tests.

    `installer_accepts_a_matching_artifact` — THE CONTROL, the test that MUST STILL PASS if checksum
    verification is removed. Serve an uncorrupted archive with a matching checksum. Assert the installer
    exits 0, and assert the installed binary exists at the install root the installer reports. This is what
    stops the pair from being vacuously red: without it, a rejection test would still pass if the fixture
    server were misconfigured and every download 404'd.

    `installer_rejects_a_corrupted_artifact_without_installing` — THE FALSIFICATION, the test that MUST
    FAIL if checksum verification is removed. Three phases, in the `quarantine_gate.rs` shape:

    1. Serve an archive with exactly one byte flipped, leaving the checksum file unchanged. Assert the
       installer exits non-zero.
    2. Assert the install root contains NO installed binary. This is the fail-CLOSED half and it is the
       assertion that distinguishes "verified before installing" from "installed then complained" — a
       non-zero exit alone does not prove ordering, and DIST-03's text is specifically about failing
       closed. Assert the failure output names the mismatch (a checksum/verification token from the
       installer's own error string), so a non-zero exit caused by an unrelated fault cannot masquerade as
       a pass.
    3. Prove the rejection is attributable to checksum verification and nothing else: build a stripped copy
       of the installer with only the checksum-verification path removed, held by an RAII guard that
       deletes it on drop including on a panicking unwind. Run the stripped copy against the SAME corrupted
       artifact and assert it exits 0 and DOES install the corrupt binary. That inversion is what makes
       phase 1's assertion load-bearing rather than incidental.

    Add a module-level comment stating the pair contract explicitly and by function name: which test must
    fail under removal of checksum verification, and which must still pass. A future reader must be able to
    tell from the file, without consulting the plan, that this is a control-plus-falsification pair.

    Keep the claim inside D-06's boundary. These tests prove the installer rejects an artifact whose bytes
    do not match its published checksum. They do NOT prove the release workflow was uncompromised, and no
    comment, test name, or assertion message in this file may imply otherwise — an attacker who can
    substitute the archive can substitute the checksum beside it.

    Run the tests the way CI runs them, not only the way `cargo test` does: CI uses `cargo nextest`
    (process-per-test), so a green `cargo test` is not evidence about CI. Verify with
    `cargo nextest run -p famp --profile ci -E 'binary(installer_checksum_gate)'` and record the result.
    Then verify by SHA that the check-run actually executed: this plan's commits touch `crates/**`, which
    is not in `ci.yml`'s `paths-ignore`, so a `total_count` of 0 is blocking.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Release asset -> user's filesystem | The installer writes an executable into a directory on the user's PATH; whatever bytes survive verification are what the user runs. |
| Test process -> developer's home directory | An installer test that does not redirect `CARGO_HOME` would overwrite the real `~/.cargo/bin/famp`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-16-01 | Tampering | Corrupted / truncated download reaching the install directory | high | mitigate | `installer_rejects_a_corrupted_artifact_without_installing` asserts non-zero exit AND an empty install root, so verification demonstrably precedes the write. |
| T-16-02 | Tampering, Spoofing | Compromised release host substituting archive and checksum together | high | accept | Explicitly out of DIST-03's scope per D-06; the test file is forbidden from claiming otherwise, and 16-04 states the boundary in the docs. Signing is the named follow-up. |
| T-16-09 | Denial of Service | A test binding a fixed ephemeral port, flaking ubuntu-only CI | low | mitigate | Bind `127.0.0.1:0` and read `local_addr()`; an acceptance criterion greps for literal ports. |
| T-16-10 | Tampering | The test itself clobbering the developer's installed `famp` | medium | mitigate | `CARGO_HOME` and `HOME` redirected to per-test `TempDir`s; a before/after digest of `~/.cargo/bin/famp` is an acceptance criterion. |
