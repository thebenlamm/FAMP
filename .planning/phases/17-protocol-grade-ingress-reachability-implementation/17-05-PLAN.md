<objective>
Give the gateway an inbound path that works from behind NAT: a polling relay-fetch loop that authorizes each drain with the Ed25519 key the gateway already holds, pulls opaque bytes from the relay, and feeds them through the exact same ingest core as a direct HTTPS POST. Then prove REACH-04 on loopback with three processes and no direct peer URL anywhere in the configuration.

Purpose: the egress half of the relay path needs no code at all — pointing `--peer <domain>=<relay-url>` at the relay already works. The inbound half is the whole gap: a NAT'd gateway cannot accept the relay's connection, so it must fetch. This plan closes that and proves both directions.

Output: `relay_fetch.rs`, a reduced-not-widened `main.rs` flag surface, and a three-process bidirectional e2e.

**Authorization mechanism (D-26, settled — do not re-open):** signed fetch, not a bearer credential. The gateway already loads an Ed25519 signing key at startup for egress; the fetch loop reuses it. The relay stores only the matching PUBLIC key. Nothing new is generated, nothing new is pasted, and nothing secret exists in this gateway's relay configuration. Plan 04 built the shared signing and verification routine; this plan is its only client.

**Disclosure that must survive into Phase 18 (D-25 -> D-29):** the relay this loop fetches from terminates TLS and sees plaintext message bodies. FAMP signs but does not encrypt. **The relay operator can read every message that transits the box.** That is a property of the model, not a bug in this code, and Phase 18's follower doc must state it plainly — a second person cannot meaningfully consent to using Ben's relay without knowing it. Nothing in this plan may describe the relay path as private, encrypted, or trustless.

**Gating bar (D-01):** this plan is what makes the gateway reachable from the open internet. It ships only alongside INGR-01 through INGR-08 (plans 01-03), never ahead of them — `depends_on` encodes that, and the wave ordering is the enforcement.
</objective>

Module doc, four paragraphs:

1. Why this loop exists: a gateway behind NAT cannot accept the relay's inbound connection, so it polls. The egress half needs no new code because `--peer <domain>=<relay-url>` already reaches the relay.
2. How a drain is authorized (D-26): each fetch carries an Ed25519 signature over a canonical authorization form built by the relay crate's own signer. Document the backoff choice: a relay that is down should not be hammered once a second indefinitely, and REACH-05's failure surface (plan 06) is what tells the operator about it, so the loop's job is to survive and recover, not to alert.

Define `pub enum RelayFetchError` with `Transport`, `MalformedResponse`, `Unauthorized`, `RateLimited`, `AuthBuild`, and `BadRecipient`, using `thiserror` and the project's value-naming `#[error(...)]` convention. Keep these distinct rather than collapsed — an operator debugging a relay must be able to tell "the relay is down" from "the relay does not know my key yet" from "I am being throttled" from "the relay sent me something I could not parse." `Unauthorized` and `RateLimited` are separate variants precisely because one is a standing misconfiguration and the other clears on its own; treating them alike is how an operator ends up debugging the wrong thing.

Define `pub(crate) fn decode_fetch_batch(body: &[u8]) -> Result<Vec<(famp::Principal, Vec<u8>)>, RelayFetchError>`. Parse the response object, iterate the envelopes array, parse each entry's recipient string through `famp::Principal::from_str`, and base64url-decode each body with the same strict unpadded URL-safe engine the relay encodes with. Any malformed entry fails the whole batch rather than being skipped — a silently skipped envelope is an undelivered message with no error anywhere, which is the exact failure REACH-05 exists to remove.

Note that in a comment so nobody "simplifies" it into a shared handle later.

Compute the audience ONCE before the loop with the relay crate's `normalize_audience` applied to `relay_base`, and comment that both sides call that same function so the comparison is exact equality over one shared normalization rather than two hand-written ones that drift.

Loop forever. Each iteration:

- build the fetch URL by joining `relay_base` with the concrete form of `RELAY_FETCH_ROUTE` for `own_domain`;
- call the relay crate's `sign_fetch_auth` with the key, the precomputed audience, `own_domain`, and the current UTC instant, and attach the resulting header pairs to the request. Do NOT assemble the signed form here and do NOT mint the nonce or format the timestamp here — the signer owns all of that, and a locally-built form is the second definition this design exists to avoid. A signing failure is `AuthBuild`, logged and backed off like any other failure rather than propagated;
- on a 401 or 403, log a distinct, loud, ACTIONABLE line: the relay accepted the request shape but did not authorize the drain, and the most likely cause by far is that the relay operator has not yet added this gateway's public key for this domain. Name the concrete remedy in the log line — the peer runs `famp peer export` and sends the operator the public-key field, and the operator adds a `--domain` entry and restarts the relay (D-27's accepted friction, surfaced at the exact moment it bites). Then back off. This will not fix itself, and the log must say so rather than repeating a generic transport error;
- on a 429, back off WITHOUT the misconfiguration log — a rate limit is transient and messages stay queued until their TTL;
- on a transport error, log with the Debug chain per the OBS-01 convention in `egress.rs`, and back off with a cap at `RELAY_FETCH_BACKOFF_MAX_MS`;
- on success, reset the backoff, `decode_fetch_batch` the body, and for each entry call `ingress::ingest_inbound(&recipient, &bytes, &state).await`, logging any `IngressError` with the reject reason and continuing to the next entry.

Never propagate a panic and never return — mirror `run_egress`'s stated contract that a down peer or one malformed envelope must not take the gateway process down.

Never widen `ingest_inbound`'s visibility beyond `pub(crate)`; `relay_fetch.rs` is in the same crate.

Write the `decode_fetch_batch` cases from `<behavior>` as unit tests in this module. Write the two authorization-agreement cases as unit tests that call the relay crate's verifier directly on what this module's signer produced — that is what makes client/server agreement a test rather than an inspection, and it will catch an audience or domain-binding mistake without needing three processes.
