# Quick Task 260808-uq0 — Fix the pairing principal mismatch

## Problem (verified, do not re-derive)

`famp pair redeem` pins the redeemer under a principal that no envelope ever
carries, so every follower→inviter message is rejected.

| Step | Location | Behavior |
|---|---|---|
| redeemer proposes its principal | `cli/pair/redeem.rs:102` | hardcoded `format!("agent:{own_domain}/gateway")` |
| inviter pins it verbatim | `cli/pair/status.rs:181-206` | pins `agent:<follower-domain>/gateway` |
| follower sends | `cli/send/mod.rs:679` | `from = agent:<follower-domain>/<identity>` (the `--as` name) |
| inviter's gateway verifies | `famp-gateway/src/verify.rs:105` | `keyring.active_key(&from)` |
| lookup | `famp-keyring/src/lib.rs:257` | exact `self.map.get(principal)`; miss → `Unpinned` |

Net: `.../gateway` is pinned, `.../<name>` arrives, lookup misses, envelope
rejected as `UnpinnedKey`. **Bidirectional federation is impossible.**
Inviter→follower works only because `famp pair invite --as` already names a
real sender principal.

## Constraint that defines the fix

`famp-keyring/src/lib.rs:118-119,160-163` — the same pubkey under two
DIFFERENT principals is `DuplicatePubkey`, **fatal at keyring load**. A host
has exactly one gateway identity key, therefore exactly one pinnable sender
principal. It MUST equal the `from` that `send` builds.

Ruled out, do not attempt: pinning aliases; adding a leaf-name fallback to
the keyring lookup. Both are dead ends against this constraint.

## Design decisions

**D1 — `--as` flag, never a positional.** `redeem.rs`'s docstring states
PAIR-06: a code-shaped invocation must be rejected by clap before any code is
read. A positional would silently swallow word 1 of a pasted five-word code.

**D2 — the domain half is derived, never typed.** `--as` accepts either a
bare leaf (`alice`) or a full principal (`agent:<domain>/alice`). A bare leaf
is combined with `own_domain::resolve_own_domain(None, home)` — the same call
`send/mod.rs:679` uses. A full principal must have its authority *equal* that
resolved own-domain; otherwise error. Rationale: the follower is a stranger
following a guide and may not know their own domain string. Deriving it makes
divergence structurally impossible rather than merely validated. Accepting the
full form too is deliberate — the guide shows one form and users copy the
other from the inviter's command.

**D3 — `--as` is REQUIRED, not optional-with-default.** An optional flag
defaulting to `gateway` silently preserves the bug for anyone who omits it.
This is a breaking CLI change against published `v1.1.0-rc.1`, and that is
acceptable: rc.1's behavior is broken, so there is no working deployment to
break. Any keyring already pinned under `.../gateway` is non-functional.

**D4 — `invite.rs`'s printed artifact must change with it.** `invite.rs:180`
prints the redeem command the follower runs. With `--as` required, that
printed command becomes wrong. It must print a clearly-marked placeholder
(`--as <your-agent-name>`), since the inviter cannot know the follower's name.

### Task 1 — Write the invariant test (RED first)

**Files:** `crates/famp/tests/pair_cli.rs`

**Action:** Add a test asserting the real invariant, not flag parsing:

> the principal the pair flow pins == the `from` principal
> `build_remote_envelope_value` constructs for the same identity

Construct both sides for identity `alice` under a fixed own-domain in a
tempdir, and assert equality. If `build_remote_envelope_value` is private,
assert against the exact same `format!("agent:{own_domain}/{identity}")`
construction and add a comment naming `send/mod.rs:679` as the source of
truth, so a future divergence is traceable.

**Verify:** Run it BEFORE any fix and confirm it FAILS with the pinned
principal ending in `/gateway`. Record the red output in the summary. A test
that passes before the fix is testing nothing — that is the whole point of
this task. Then confirm one existing `pair_cli` test still passes, so the red
is specific and not an environment failure.

**Done:** Test exists, fails red for the right reason, and the failure message
names both principals.

### Task 2 — Add `--as` to `famp pair redeem`

**Files:** `crates/famp/src/cli/pair/redeem.rs`, `crates/famp/src/cli/pair/invite.rs`

**Action:**
1. Add a required `--as <AS_IDENTITY>` arg to redeem's clap args struct
   (alongside `--from` / `--trust-cert`). Keep PAIR-06 intact: no positional,
   and the value must not be code-shaped.
2. Replace the hardcoded `format!("agent:{own_domain}/gateway")` at
   `redeem.rs:102` with a resolution helper implementing D2: bare leaf →
   combine with resolved own-domain; full principal → require authority ==
   resolved own-domain, else a clear `CliError` naming both values.
3. Update `invite.rs`'s printed artifact so the redeem command it prints
   carries `--as <your-agent-name>` as a marked placeholder.

**Verify:** `cargo test -p famp --test pair_cli` — Task 1's test now GREEN.
Also confirm a five-word code passed as a bare argument is still rejected by
clap (PAIR-06 red path).

**Done:** Redeem pins the principal the follower will actually send as; the
invite artifact tells the follower to supply it.

### Task 3 — Fix `pin()` save-before-validate ordering

**Files:** `crates/famp/src/cli/pair/status.rs`

**Action:** `pin()` at lines 273-285 calls `save_to_file` BEFORE the reload
validation, so a pin that fails validation leaves a keyring on disk that will
refuse to load and brick the gateway at next start. Validate before saving, or
write to a temp path in the same directory and rename only after the reload
succeeds.

Keep it surgical. If it cannot be done without restructuring `pin()`'s
signature or touching other files, STOP and report rather than expanding.

**Verify:** `cargo test -p famp --test pair_cli`.

**Done:** A rejected pin leaves the previous keyring intact on disk.
