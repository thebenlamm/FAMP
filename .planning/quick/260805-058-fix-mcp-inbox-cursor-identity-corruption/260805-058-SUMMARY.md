# Quick Task 260805-058: Fix MCP Inbox Cursor Identity Corruption Summary

> ⚠️ **READ THE `## CORRECTION` SECTION AT THE END OF THIS FILE FIRST.** The TOCTOU root
> cause this task was planned against was falsified by post-implementation adversarial
> review and retracted in commits `a246fed`–`d5d9530`. Everything between here and that
> section reflects the original, partly-wrong framing and is kept only as a record.

**Made the on-disk read cursor unable to sit past EOF (four already-corrupt cursors self-heal
on their next read), and added an explicit `rebind: true` opt-in guard so a subagent can no
longer silently hijack its parent window's registered MCP identity.**

## Performance

- **Duration:** ~35 min
- **Tasks:** 3 (Task 1: TOCTOU + EOF clamp; Task 2: rebind guard; Task 3: lint/regression sweep + `just install`)
- **Files modified:** 5
- **Commits:** 3 (Task 3's `just lint` sweep required one follow-up code commit — see below)

## Accomplishments

- `tools::inbox::call()` now snapshots `session::active_identity()` exactly once and reuses it for both the broker `act_as` argument and the cursor write-through filename, closing the read/write identity race a concurrent `famp_register` could win.
- New pure helper `cursor_write_target(current, next_offset, mailbox_size)` clamps the disk-cursor write to the mailbox's real byte size. The write now fires on `target != current` (not `target > current`), so a cursor that has already landed past EOF regresses to the correct value on the next `famp_inbox` call instead of staying permanently blind.
- `tools::register::call()` gained a rebind guard: registering under a DIFFERENT identity than the one already bound on this MCP session now fails with a typed `envelope_invalid` error naming both identities and the `rebind` escape hatch, checked and rejected BEFORE the broker round-trip so nothing mutates. `rebind: true` performs the takeover explicitly. Same-name re-register and first-time register are unchanged.
- `server.rs`'s `famp_register` `inputSchema` gained a `rebind` boolean property, and the tool description now states the binding is process-wide for the entire window including every subagent, and that subagents must not call it.
- `inbox.rs`'s module doc no longer claims cursor advancement is CLI-only (false since the write-through landed); it now describes the write-through and names the EOF clamp.
- `session.rs` got a doc-only note flagging that `set_active_identity` (currently zero production callers) would bypass the rebind guard if ever wired to a new caller.

## Decisions Made

- `cursor_write_target` is written as a manual `if`/`else` chain rather than `current.max(next_offset).min(mailbox_size)` as literally specified in the plan's action text — `u64::max`/`min` (the `Ord` trait methods) are not `const fn` on stable Rust 1.89, and the plan itself specifies `const fn cursor_write_target(...)`. Behavior is identical; verified against all six of the plan's own test cases including the exact live corrupt-cursor numbers.
- `rebind_rejection()` was extracted from `register.rs::call()` as a separate pure function during the Task 3 lint sweep. The inline guard (as first written in Task 2) pushed `call()` to 101 lines, tripping `clippy::too_many_lines` under `just lint`'s pedantic lint set — a genuine blocking-issue auto-fix (Rule 3), not scope creep. The guard's decision logic and the exact error-message text are byte-identical to what Task 2 committed; only the code's location moved. All 5 rebind integration tests and the full `mcp_register_whoami` suite were re-run green after the extraction.
- `EnvelopeInvalid` (not a new `BusErrorKind` variant, not `NameTaken`) is the error kind for the rebind rejection, per the plan's explicit reasoning: `NameTaken` already means "a different live client holds this name" on the broker path, and a new variant would force a change to `famp-bus`'s exhaustive `BusErrorKind::ALL` array and its consumer-stub tests — both out of scope for a `famp`-CLI-layer-only fix.

## CORRECTION (post-review, commits a246fed · 074d0ef · d198353 · d5d9530)

**Everything above that attributes this bug to a TOCTOU is WRONG and has been retracted in
the code.** Two adversarial reviewers were run on the diff only; one falsified the root cause
this task was planned against. The orchestrator re-verified both facts directly before
accepting the retraction:

1. `crates/famp/src/cli/mcp/server.rs::run` is a strictly serial
   `read_msg → await dispatch_tool → write_msg` loop, and there is **no `tokio::spawn`
   anywhere under `crates/famp/src/cli/mcp/`**. One `famp mcp` process therefore never has
   two tool calls in flight, so no `famp_register` can land between two
   `active_identity()` reads inside `inbox.rs::call()`. **The race does not exist.**
2. `crates/famp/src/cli/broker/mailbox_env.rs:181-243` — the broker's `next_offset` is
   always a complete-line boundary. `crates/famp-inbox/src/append.rs:98-111` writes a
   record's body and its `\n` in two separate `write_all` calls, so our own
   `metadata().len()` could observe the mailbox **mid-record** — the skip direction.

**What changed as a result:**
- `read_mailbox_size` and `cursor_write_target` were **deleted** (and their 8 unit tests with
  them — lib count 367 → 359). The write-through target is now simply `out.next_offset`,
  written on `target != current`. That is strictly better than the stat-based clamp: no
  mid-record window, and the monotonic `max()` floor is gone because the broker returns the
  file-end boundary regardless of `since` (including `since: 0`), so the floor was guarding
  an input the broker cannot produce.
- The single `active_identity()` snapshot was **kept** but is now documented as a defensive
  invariant against a future concurrent dispatcher, not a fix for an observed race.
  `call_body_reads_active_identity_exactly_once` is retained with an honest doc comment,
  including its own weakness: it counts source *text*, so a future read via
  `session::state().lock().await.active_identity` would evade it.
- The rebind-rejection message was reordered to **lead with the bound state and the
  `rebind: true` remedy**. The guard is first-writer-wins with no role awareness, so if a
  subagent binds first it is the legitimate parent window that gets refused; the old text
  led with "subagents must NOT call famp_register" and buried the way out.
- `.claude/skills/famp-setup/SKILL.md:182` — "idempotent" qualified to same-identity-only.

**STILL OPEN — the actual root cause is unknown.** What wrote `14334` into
`~/.famp/mailboxes/.lane-x-merge.cursor` (exactly the byte size of a *different* identity's
mailbox, `LANE-L.jsonl`) is unexplained. The `next_offset` write-through heals the four
corrupt cursors on their next read, and the rebind guard closes the identity-hijack class the
first bug report documented, but neither explains the cross-identity byte value. This needs a
separate investigation before anyone claims the incident is understood.

`crates/famp/assets/slash_commands/famp-register.md` was deliberately left untouched: it
prescribes zero argument keys today, and `crates/famp/tests/slash_command_assets.rs:400-419`
only skips the required-key gate while it stays at zero — adding a `rebind: true` span there
makes the gate demand an `identity` bullet in the same edit.
